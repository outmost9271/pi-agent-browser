# pi-agent-browser 容器适配、CDP 补全与安全加固开发方案

- 文档版本：1.0
- 编写日期：2026-09-08
- 部署根目录：`/docker/agent-browser`
- 状态：开发计划；尚未实施、尚未通过验收。
- 本轮交付范围：仅持久化开发方案、技术路线与检查标准，不修改运行部署、不重启容器、不迁移登录态。

## 1. 用户要求与不可变边界

### 1.1 必须完成

1. 保持现有结构：pi 与原生扩展运行在宿主机；真正的 `agent-browser` 控制端、Chrome 及浏览器运行依赖运行在容器。
2. 将基础命令转发升级为完整、可维护、可验证的适配层。
3. 将已声明的 CDP 接口补全为真实可连接、可操作、可恢复的服务，而不只是发布端口。
4. 修复浏览器配置未加载及字段错误，并验证配置实际效果。
5. 实施容器与浏览器进程层面的安全加固。
6. 保留现有网络与业务操作安全策略，不改变其允许、拒绝和确认行为。
7. 保护既有数据、登录态、凭证库与加密密钥，提供可验证的升级和回滚路径。

### 1.2 不得借修复之名改变的事项

| 项目 | 必须保持的行为 |
| --- | --- |
| 域名限制 | 不新增 `allowedDomains` 或 `AGENT_BROWSER_ALLOWED_DOMAINS`，维持目前未启用状态 |
| 业务动作策略 | 不新增 `actionPolicy` 或 `AGENT_BROWSER_ACTION_POLICY`，维持目前未启用状态 |
| 动作确认 | 不启用 `confirmActions`、`confirmInteractive` 或对应环境变量，不新增人工确认环节 |
| 互联网出站 | 不新增出站防火墙、强制代理、域名代理白名单、DNS 过滤或内网访问限制 |
| 运行期代理 | 不因宿主机环境或 fnm 包装而意外向浏览器透传标准代理变量；保留现有运行期网络行为 |
| 构建期代理 | 保留当前构建下载所用配置，不随本项目擅自更改 |
| CDP 宿主机暴露范围 | 保持 `127.0.0.1:9222`，不改成所有网卡、不额外发布端口 |
| Docker 网络 | 保留当前桥接网络；不改为宿主机网络、不新增网络访问控制策略 |
| 账号与凭证 | 不修改账号权限、不轮换或重建既有密钥、不清空登录态 |
| pi 工具权限 | 本项目不新增 pi 业务审批策略，不改变用户现有工具授权方式 |

容器内核能力、系统调用过滤、浏览器沙箱、文件权限、只读配置和资源限额属于本次加固范围。它们不能被用来隐式阻断原本允许的正常浏览、表单、脚本、上传或下载业务。

CDP HTTP/WebSocket 转发仅补全现有端口的功能。连接路径校验和防止任意目标转发属于接口正确性，不应新增对网站、CDP 方法或业务动作的过滤。若后续希望启用 CDP 令牌、修改来源准入或改变端口绑定，必须作为独立变更重新确认，不在本次偷偷加入。

### 1.3 “真正完整可用”的定义

完整性以固定版本的原生工具契约和本文验收矩阵为准，而不是“某次能打开网页”。必须同时满足：

- 所有浏览器核心输入模式都经过真实原生工具路径验证。
- 参数、标准输入、环境、工作目录、文件、会话、超时和取消均有明确契约。
- 主通道及 CDP 通道均可操作真实浏览器，并具有独立的故障诊断。
- 所有关键测试通过，且结果和证据可复查。
- 不通过关闭扩展校验、关闭脚本隔离、放宽容器权限或忽略错误换取通过。
- 不将未执行、环境不具备、上游报错或仅命令成功的测试标记为通过。

完整可用不代表改变上游能力边界：例如恢复 URL、Cookie 和存储不等于恢复未提交表单、JavaScript 内存或完整历史；已经派发的网页操作不能靠取消请求撤销。

### 2.3 已确认的实现缺口

1. 包装脚本只对顶层 argv 的四类路径前缀进行单向替换。
2. `stdin` 批处理、原始批处理字符串和返回 JSON 中的路径没有完整适配。
3. 没有把扩展设置的运行环境传入 `docker exec`，也没有“清除变量”的语义。
4. 没有传递或适配工作目录，宿主机与容器相对路径、项目配置发现范围不同。
5. 宿主机取消 `docker exec` 不足以证明容器 CLI、守护进程中的任务及后续批处理步骤已经停止。
6. `/docker/agent-browser/config/agent-browser.json` 未挂载或复制到容器加载位置，也没有显式 `--config` 或 `AGENT_BROWSER_CONFIG` 指向它。
7. 模板使用了需要修正的 `headless`、`autosaveIntervalMs`、`stateExpireDays` 等配置方式。
8. CDP 目前只有端口发布和备用脚本，没有完整的浏览器启动、发现地址、连接恢复和独立验收。
9. 健康检查使用 `CDP 检查 || doctor`，会把“CDP 不工作但安装诊断通过”显示为健康。
10. 容器增加了 `SYS_ADMIN`，并设置 `seccomp:unconfined`；尚未验证实际浏览器沙箱状态。
11. 当前没有明确的内存、CPU、进程数限额，根文件系统可写。
12. 镜像依赖列表没有明确安装 `ffmpeg`；录制停止与编码必须单独补齐、验证。
13. 主 README、数据目录 README 和配置目录 README 与实际部署有不一致描述，必须同步修订。

并非所有状态检查都依赖宿主机 PID：已安装扩展使用上游 `session info` 检查守护进程。因此不能泛化成“容器内 PID 不同导致所有会话检查失效”。需针对真实实现逐项验证。

## 3. 技术路线与最终架构

### 3.1 总体决定

采用“宿主机受控适配器 + 容器执行代理 + 原生扩展最小后端集成 + 独立 CDP 服务管理”的方案。

不继续把所有逻辑塞进 Bash 字符串替换，也不改成宿主机运行真正的 `agent-browser`。保持用户要求的部署边界。

```text
宿主机
  pi
    └─ pi-agent-browser-native（保持 agent_browser 工具契约）
        └─ Docker 执行后端
            ├─ 参数、环境和模式上下文
            ├─ 文件处理与产物验证
            ├─ 会话、租约与取消
            └─ /usr/local/bin/agent-browser 兼容入口
                └─ 宿主机桥接程序
                    └─ docker exec -i，受控标准输入输出协议
                        └─ 容器执行代理
                            ├─ 真正的 agent-browser CLI 与守护进程
                            ├─ 主通道浏览器实例
                            └─ CDP 实例管理器
                                └─ CDP 专属 Chrome 与端口网关

外部 CDP 客户端 / 宿主机测试客户端
  └─ 127.0.0.1:9222
      └─ 容器 CDP 网关
          └─ 被登记、被管理的 Chrome CDP 端点
```

### 3.2 为什么需要扩展后端集成

扩展不仅启动子进程，还会在宿主机：

- 验证文件存在性、更新时间、别名和路径所有权；
- 管理恢复池、项目身份和清理租约；
- 检查调用模式，尤其是 `script` 的隔离；
- 创建产物父目录并保存输出；
- 维护分支、恢复与关闭语义。

单个可执行文件无法透明拦截这些宿主机内的文件系统操作。因此本项目允许并要求：在必要边界增加 Docker 后端接口，保留原始本地后端，不用伪造文件和放宽验证代替适配。

实施顺序：先验证已有公开扩展点；不足时维护基于 `0.6.8` 源码的最小补丁包。不得直接修改已安装包的 `dist/` 作为最终交付。补丁必须独立、有测试、可重建，并尽可能整理为可提交给上游的改动。

若上游 `agent-browser` 的自动禁用沙箱或请求取消机制不足以满足本方案，允许维护基于 `0.36.0` 的最小源码补丁，并保留版本、提交、差异和二进制哈希。不能把自定义行为冒充上游已有能力。

### 3.3 实现语言与依赖

- 宿主机适配器、扩展集成和测试：TypeScript，使用现有受控 Node 环境。
- 容器执行代理：优先 Rust，小型独立二进制，负责协议、进程组、租约和文件操作，不需要把 pi 安装到容器。
- CDP 网关优先复用维护良好的 HTTP/WebSocket 库，不自写 WebSocket 帧协议。
- 宿主机所有 Node/npm/fnm 操作必须经 `/pi/node/tool/bin/fnm`；项目依赖、构建输出及锁文件归项目所有。
- 若新增容器 Node 执行入口，也必须遵守当前环境的 Node 管理规范，不能临时依赖宿主机系统 Node。
- 不引入 Python 作为隐藏运行依赖；如以后确需使用，先遵守现有受控 uv 规范。
- 固定直接依赖、镜像基础版本和摘要；升级受支持的基础镜像需经过同一套兼容性测试。

### 3.4 能力覆盖边界

| 原生模式 | 目标 |
| --- | --- |
| `args` | 保持固定上游版本的浏览器命令与参数语义，完整支持文件输入输出及批处理 |
| `semanticAction` | 使用扩展现有编译逻辑，不重复实现定位器语义 |
| `job` | 编译后的每一步统一经过路径、超时与生命周期处理 |
| `qa` | 保留失败即停、诊断缓冲区和截图验证语义 |
| `script` | 原有沙箱仍在宿主机；内部调用统一进入 Docker 后端，严格独立会话与配置 |
| `sourceLookup` | DOM/React 证据来自容器浏览器，源码扫描仍在 pi 的宿主机工作目录 |
| `networkSourceLookup` | 请求证据来自同一浏览器会话，工作区扫描和候选说明保持原生逻辑 |
| `electron` | 保持宿主机应用发现与生命周期的原生职责；不得将宿主机应用可执行路径误映射为容器 Chrome 路径 |

本项目的完整浏览器交付不能通过关闭 `script`、`job`、`qa` 等核心模式来达成。Electron 操作系统专属能力、iOS 和需要第三方账号的云服务单独列出环境依赖；不得声称 Linux Chrome 容器能原样运行任意宿主机桌面应用。

## 4. 传输协议与执行契约

### 4.1 不经过 Shell 拼接执行

宿主机兼容入口只负责稳定定位桥接程序并转交 argv。主执行路径使用参数数组和标准输入，不执行 `eval`，不构造 `sh -c` 业务命令，不把口令、页面脚本或批处理 JSON 拼进 Docker 命令字符串。

宿主机到容器使用带版本号的内部协议。建议请求字段：

- `protocolVersion`、`requestId`、截止时间；
- 完整 argv 数组；
- 逻辑宿主机工作目录与映射后的运行目录；
- 明确的模式上下文：普通、脚本隔离、连接会话或服务自有任务；
- 环境变量设置和删除集合；
- 标准输入内容或有长度上限的分块；
- 输入、输出、配置和配置目录的路径清单；
- 会话、命名空间和生命周期所有权引用。

这些是自研桥接协议字段，不是上游 `agent-browser` 原生选项。模式身份必须来自可信扩展调用上下文，不能通过会话名前缀猜测，也不能让网页内容覆盖。

### 4.2 标准输入输出

- 原生工具的秘密数据使用受控输入通道，桥接器不得将原本在 stdin 中的口令复制到 argv、审计正文或错误日志。
- 若调用方主动在兼容 CLI 的 argv 中写入秘密，桥接器无法事后消除初始进程的暴露；须保留原生警告并推荐 stdin，不能宣称这种调用也具有同等保密保证。此限制不作为新增业务动作拒绝策略。
- 输入协议和上游 `stdin` 必须分层，支持原样传递 `eval --stdin`、批处理和 `auth save --password-stdin`。
- 保留 stdout、stderr、退出码、信号和超时状态的区别。
- 对外 stdout 只提供上游兼容结果；诊断信息不能污染 JSON。
- 原样支持帮助、版本等纯文本输出，不强迫它们变成业务 JSON。
- 输出使用有界缓冲和分块传输；超过内存阈值时使用受控临时文件，不能无限累积内存。
- 不把任意字符串中的容器路径全局替换；只能根据命令与已知结构化字段转换运行时路径。
- 页面文本、URL、JavaScript 源码、选择器、认证内容与普通字符串不得因“像路径”而被修改。
- JSON 解析失败应返回结构化故障，不把未经脱敏的整个原始结果持久化。

### 4.3 超时、取消与执行确认

每个请求必须有状态：已接收、已准备、已派发、执行中、已完成、已取消、结果不确定。记录容器实例身份和任务身份，避免容器重建后的旧 PID、旧请求或旧句柄被误用。

- 宿主机超时或取消必须传入容器执行代理。
- 容器代理以请求为单位管理 CLI 进程组，分阶段终止，并清理输入暂存文件。
- 增加宿主机失联租约；宿主机异常退出时不能遗留无限运行的任务。
- 验证守护进程是否会在 CLI 退出后继续执行批处理。如果会，必须接入或补充请求级取消，在每个后续步骤前检查取消状态。
- 不能只验证 CLI PID 消失就宣布取消成功。
- 已经派发的点击、导航或网络请求可能不可撤销；返回已派发证据，不承诺回滚网页业务。
- 共享或调用方所有的浏览器不得为清理某个请求而直接整体杀死。
- 不能确定是否执行的修改性步骤禁止自动重试。请求去重也必须区分“拒绝重复派发”和“重放既有结果”。
- 多步骤任务取消后必须证明未执行剩余步骤，或明确报告结果不确定并使验收失败。

## 5. 路径、工作目录与产物适配

### 5.1 统一文件处理，不做无差别文本替换

建立路径分类器，复用扩展与上游固定版本的参数语法。支持直接 argv、原始批处理字符串以及 `stdin` 批处理；遵循上游“原始批处理参数优先于 stdin”的有效输入规则。

必须分类处理：

- 输入文件：上传、初始化脚本、状态加载、Cookie 导入、证书及显式配置；
- 输出文件：截图、PDF、下载、下载等待、状态保存、录像、HAR、跟踪和性能记录；
- 配置目录：浏览器 profile；
- 工作目录与项目配置；
- URL：只在明确需要的 `file://` 输入上做协议级处理，普通 HTTP、HTTPS、WebSocket URL 不作路径替换；
- `outputPath`：仍由宿主机扩展保存工具结果，不误当成容器浏览器产物。

### 5.2 共享目录与按需暂存

1. 保留四个现有持久化挂载。
2. 对产物目录可增加同绝对路径别名挂载，减少新命令与批处理的路径转换；必须登记两个名字是同一存储，避免绕过重复写入和录制占用检查。
3. 不整体挂载宿主机根目录、主目录或 pi 凭证目录。
4. 现有挂载之外的合法显式输入，通过每次调用专属的暂存目录传入，或使用经过登记的项目只读挂载。
5. 挂载外的合法显式输出先在容器暂存，完成后回传并原子提交到用户指定的宿主机路径。
6. 不能把“只支持四个目录”描述成完整支持任意显式产物路径。
7. 对含相对资源的本地 HTML、初始化脚本或项目输入，必须声明并处理资源根目录；不能只复制入口文件后声称支持完整本地页面。
8. 未声明的任意宿主机文件系统不会自动暴露给网页或容器。不能通过解析并改写任意 JavaScript 来模拟宿主机文件系统。

### 5.3 工作目录与项目配置

- 桥接协议保留 pi 的真实逻辑工作目录。
- 有对应挂载时使用实际对应的容器工作目录；无挂载时使用明确的任务工作区映射，不能静默退回 `/home/agent`。
- 相对输入、输出和配置路径必须相对于原始调用工作目录解析。
- 区分“宿主机源码扫描”和“容器命令执行目录”，不能把 `sourceLookup` 扫描范围改成容器安装目录。
- 项目配置是否加载继续遵循原有 pi 信任决定和明确的上游配置选择，不能通过复制项目文件绕过项目信任。
- 对映射受限、缺少资源根或无法安全暂存的调用，在派发前清楚失败，禁止在错误目录继续运行。

### 5.4 所有权与权限

当前 pi 文件准备可能由宿主机 root 执行，容器浏览器则由 UID 1001 执行。宿主机新建的 `0755 root:root` 子目录可能使容器无法写入，这是必须覆盖的实际问题。

- Docker 后端应在执行侧准备浏览器产物目录，或在明确的产物根上使用最小组权限/默认 ACL。
- 宿主机私有会话文件和扩展溢出文件不能因此授权给容器。
- 不使用 `chmod -R 777`，不通过让 Chrome 以 root 运行解决写权限。
- 私有 socket、配置目录与恢复状态分别按照所属运行时 UID 校验，不伪装成宿主机 UID。
- 对符号链接、硬链接、路径穿越、已存在文件和同文件别名沿用或加强原生验证。
- 容器返回的元数据不能授权新的宿主机写路径；宿主机只接受派发前已登记的目标。
- 回传只能提交预期的普通文件，不能把容器提供的符号链接、设备或额外路径导入宿主机。

### 5.5 产物一致性

为每个产物记录请求路径、逻辑宿主机路径、运行时路径、实际存储位置、调用身份、大小、时间及必要校验和。

- 容器侧检查文件产生，宿主机侧检查回传或共享文件可读，两侧一致才报告已验证。
- 已存在但本次未更新的截图等产物不能当作新证据。
- 保留原生下载等待的观察性语义；不伪造下载事件。
- 录制开始返回待完成，停止编码成功并验证文件后才报告成品。
- 继续阻止 `outputPath`、截图、下载和正在录制路径的同文件冲突。
- 显式产物关闭浏览器后保留；临时文件按租约清理。
- 原生 `artifacts`、`artifactVerification`、`artifactManifest`、附件和 `outputFile` 必须一致，而不是只改可见文字。

## 6. 环境、配置与秘密处理

### 6.1 显式环境契约

环境不是把 `printenv` 全部传入容器，也不是完全不传。

建立基于上游 `0.36.0` 的环境变量注册表，记录类型、来源、优先级、是否敏感、是否为路径、是否启动限定及模式适用性。

必须覆盖恢复键、命名空间、socket、默认操作超时、空闲超时、自动保存、配置路径、浏览器选择、启动参数、内容输出设置、状态和用户明确选择的提供商变量。

必须同时支持：

- 设置一个值；
- 明确清除一个值；
- 采用已登记的基础默认值。

容器代理需从干净、可解释的环境构建子进程，而不是无条件继承 Compose 中所有 `AGENT_BROWSER_*` 变量。宿主机标准代理不自动进入浏览器；用户显式选择的上游参数保持原生语义。

启动参数对同一守护进程必须稳定。前置探针、语义定位辅助、主命令和清理使用同一套会话环境，防止辅助命令触发隐式重启。

### 6.2 配置分层

区分三套配置：

1. pi 配置：`/agent-pi/config/settings.json`，负责加载扩展包。
2. 原生扩展配置：按扩展自己的路径和 `PI_AGENT_BROWSER_CONFIG` 规则加载。
3. 上游浏览器配置：容器内显式 `AGENT_BROWSER_CONFIG` 或 `--config`，不能与前两者混淆。

公共浏览器基础配置只包含普通默认值；登录 profile 通过明确选择启用；脚本隔离模式生成不含 profile、恢复或附加设置的独立有效配置；CDP 服务使用自己的配置与生命周期。

所有临时有效配置均由基础配置与明确调用合成，权限为私有，具有版本和摘要。不得因 `AGENT_BROWSER_CONFIG` 优先级而意外忽略基础配置，也不得合并已被上游明确替代的配置源。

### 6.3 修复模板

将现有文件修正为以下基础形式；此处是计划目标，不表示本轮已写入配置：

```json
{
  "$schema": "https://agent-browser.dev/schema.json",
  "headed": false,
  "idleTimeout": "1h",
  "downloadPath": "/downloads",
  "screenshotDir": "/screenshots",
  "contentBoundaries": true,
  "maxOutput": 50000
}
```

对应守护进程默认设置：

```text
AGENT_BROWSER_AUTOSAVE_INTERVAL_MS=30000
AGENT_BROWSER_STATE_EXPIRE_DAYS=30
```

实施时仍应核对固定 `0.36.0` 源码或该版本模式文件，不能只用可能已更新的官网表格作为字段有效性的唯一证据。未知键需要项目自身校验器报错：官方模式允许额外字段，单纯 JSON/schema 校验不足以发现所有拼写错误。

删除无效或误导性的 `headless`、`autosaveIntervalMs`、`stateExpireDays` 字段。说明性长注释放在文档，不依赖 `_comment` 参与运行时配置。

`/profiles/default` 的既有数据和用途保留，但不能把它隐式注入所有普通任务、脚本和 CDP 新实例。账户任务明确选择该 profile；未选择时保持临时/原生托管会话行为，避免修复配置后意外共享真实登录态。

### 6.4 显式挂载与加载失败处理

基础配置通过只读文件挂载进入容器，例如：

```yaml
services:
  agent-browser:
    volumes:
      - type: bind
        source: ./config/agent-browser.json
        target: /etc/agent-browser/config.json
        read_only: true
        bind:
          create_host_path: false
    environment:
      AGENT_BROWSER_CONFIG: /etc/agent-browser/config.json
      AGENT_BROWSER_AUTOSAVE_INTERVAL_MS: "30000"
      AGENT_BROWSER_STATE_EXPIRE_DAYS: "30"
```

这是合并到现有 Compose 的局部示意，不得用它覆盖全部原配置。启动前验证源路径是普通文件；缺失、错误类型、非法 JSON 或字段错误时明确失败，不能继续以未配置状态启动。

执行代理按模式生成有效配置，因此实际 CLI 使用的配置可能是私有派生文件。状态输出必须显示基础配置来源和脱敏后的有效字段，不能只展示挂载存在。

Compose 挂载和环境改变后需要重建容器实例；只执行 `restart` 不算完成部署。已经运行的浏览器启动选项通过受控的新实例生效，不暗中改变活动业务浏览器。

### 6.5 保持网络与业务策略不变的自动检查

在普通、profile、script、CDP 和恢复模式下自动断言：

- `allowedDomains` 未新增；
- `actionPolicy` 未新增；
- `confirmActions` 和 `confirmInteractive` 未启用；
- 对应环境变量没有被模板或代理悄悄注入；
- 标准运行期代理没有来自宿主机的意外继承；
- 未新增业务 CDP 方法过滤或审批流程。

内容边界和输出长度限制按原模板意图启用，并验证输出结构。它们不是域名限制或业务动作限制，也不构成对提示注入的强保证。

### 6.6 密钥与日志

- 不在文档、测试报告、日志、命令行或版本库保存真实 Cookie、口令、令牌、私钥及完整认证状态。
- 密钥与凭证库原地保留，不因权限修复重新生成。
- 状态检查只返回存在性、权限和加密方式等必要元数据。
- 日志使用请求 ID、版本、状态、耗时与脱敏路径；脚本、表单值和页面正文默认不记入运维日志。
- 数据备份单独保护；不能因为凭证库已加密就允许密钥与备份目录任意读取。

## 7. 会话、恢复与并发

### 7.1 明确所有权

分别登记：

- 扩展创建的托管会话；
- 调用方明确选择的会话；
- 一次性脚本会话；
- CDP 服务自有浏览器；
- 附加到既有 CDP 浏览器的控制会话；
- 输入暂存、产物暂存和录制租约。

记录实际容器实例身份、命名空间、上游会话名、配置目录身份及生命周期。不得仅凭名称相似或 PID 数字判断所有权。

### 7.2 保持原生会话语义

- `sessionMode: auto` 继续跟随当前托管会话。
- `sessionMode: fresh` 只在新会话成立后切换；失败时保留或明确放弃，不能悄悄回到错误目标。
- 关闭只作用于调用方有所有权的对象。
- `session info` 的运行时恢复键必须与宿主机计划一致；不能删除该验证绕过桥接问题。
- 同身份调用串行，不同身份可并发；保留命名空间 `close --all` 的屏障语义。
- 导航、标签页变化及录制生命周期后的引用失效逻辑保持原生行为。
- 原生 `nextActions` 必须返回可再次执行的宿主机工具参数，不能泄漏不可用的暂存路径。

### 7.3 恢复存储分工

- pi 分支、会话记录、项目 Git 身份和宿主机并发锁由宿主机管理。
- 容器 HOME、socket、恢复文件、加密材料和运行时文件所有权由执行侧验证。
- 后端传递受验证的存储元数据，不把容器 UID 1001 文件假装成宿主机 root 所有的私有存储。
- 恢复键继续由原生规则确定，准确传给容器；不另造与 pi 分支无关的全局登录态池。
- 临时和显式产物按原生生命周期保留或清理，恢复状态不冒充普通产物。

当前 `/pi/search` 可能不具备原生自动恢复所要求的可信 Git 工作区身份。自动恢复测试必须分别使用符合条件的可信 Git 测试仓库和普通目录；后者按原生规则不启用时，不能强行放宽校验来制造“通过”。用户显式 profile 的持久化是另一项能力，应独立验收。

### 7.4 脚本模式的特殊约束

保留 `script` 的调用次数、输出大小、时间限制和宿主机语言沙箱。所有内部浏览器调用进入同一后端，但：

- 不继承容器默认业务 profile、恢复状态、CDP、提供商或代理配置；
- 使用唯一、非持久化、非附加会话；
- 不能因 Compose 环境或全局配置而从后门重新引入被宿主机清除的设置；
- 调用前持久化清理租约，正常结束、异常、超时、分支切换和 pi 退出都验证清理；
- 普通对话会话和 CDP 服务不得被脚本替换或关闭。

## 8. CDP 功能补全

### 8.1 目标与双通道关系

主通道依旧是“宿主机适配器 → 容器 CLI”。CDP 是并存能力，不替换主通道，也不把所有 `script` 调用隐式附加到共享浏览器。

必须支持：

1. 宿主机独立 CDP 客户端直接访问 `127.0.0.1:9222`；
2. 现有 `agent_browser` 工具通过桥接后的 `connect`、`--cdp` 附加；
3. 默认公开网页用途的 CDP 实例，端点仍只发布到宿主机回环地址；
4. 显式选择的 profile 实例，在独占关系允许时启动或附加；
5. 容器重建、Chrome 退出和连接中断后的清楚恢复指引。

### 8.2 浏览器服务生命周期

增加容器内服务监督入口，替代单纯 `tail`。它负责执行代理、CDP 实例和端点网关的健康状态；不能在普通命令执行时无条件重建容器。

CDP 默认实例使用独立的专属配置目录，不偷偷接管 `/profiles/default`。如用户明确选择现有业务 profile，必须先检查没有另一浏览器占用，且不得启动第二个共享同一配置目录的进程。

普通托管会话保留原空闲超时。CDP 服务实例的保活与关闭由服务自身管理，不能被普通探针环境漂移误杀；其例外必须明确记录，不能为了 CDP 在全局关闭超时。

同一 profile 的互斥应跨主通道、CDP 通道和容器重启成立。文件锁必须结合进程身份与租约，不能只信任一个残留锁文件。

### 8.3 端点发布方案

浏览器监听容器内回环地址的受控调试端口；网关在容器 `9222` 提供标准 HTTP/WebSocket 访问，宿主机仍只发布到 `127.0.0.1:9222`。

- 网关只转发到被实例管理器登记的 Chrome，不接受任意目的主机和端口。
- 正确处理 `/json/version`、`/json/list`、协议发现、标准目标管理路由和浏览器/页面 WebSocket 路径。
- 保持标准请求方法与 CDP 消息语义，不新增业务方法过滤。
- 发现返回的 `webSocketDebuggerUrl` 必须从宿主机可达，不泄漏只能在容器内使用的地址。
- 根据固定的对外端点及允许的本地访问名称生成地址，不盲目信任任意 Host/转发头。
- 支持 WebSocket 二进制/文本、分片、背压、关闭、错误及大截图响应，具体由成熟库承担。
- 旧浏览器端点在实例重建后失效，不能被悄悄路由到另一个用户或 profile。
- 不使用 `--remote-allow-origins=*` 作为默认修复；若连接涉及 Origin，按当前实际客户端验证兼容配置，不新增宽泛放行。

端口监听必须实测：容器内服务只监听 `127.0.0.1` 不意味着 Docker 发布端口必然可达，不能只写 Compose 端口映射就通过。

计划新增独立管理入口 `pi-agent-browser-bridge`，提供 `status`、`doctor`、脱敏配置检查及 `cdp start/list/status/endpoint/stop`。这些是拟开发的桥接管理命令，不是当前已有的上游命令；控制请求仍走 Docker 标准输入输出，不新增管理 TCP 端口。

- `wrapper/agent-browser-cdp` 默认先解析已就绪的默认实例端点，再以原生附加方式调用同一个桥接器；不再盲目附加固定端口。
- 显式 profile 通过实例管理命令选择并取得实例 ID 和 WebSocket URL；不能把远程实例的 profile 选择伪装成对已连接浏览器传递一个不会生效的 `--profile`。
- 默认实例提供标准根发现路由；其他登记实例通过同一端口的实例限定路径及明确 WebSocket URL 访问，不增加宿主机端口。
- 实例限定路径必须携带不可混淆的实例代次，旧路径不能指向后来复用名称的新浏览器。
- 多实例路由的 URL 前缀与完整 WebSocket URL必须用原生 `connect` 和独立客户端实测，不能假定每种 HTTP 发现客户端都支持自定义前缀。

### 8.4 附加与关闭语义

- 连接后验证实际 URL 与目标，不把连接成功当成页面就绪。
- 多个命名会话使用目标绑定；需要时使用原生 `--pin-tab`，但不得把同浏览器多标签误称为账号隔离。
- 同一 CDP 浏览器被多个客户端操作时共享状态是协议事实；应检测漂移并给出恢复，不承诺无冲突。
- 关闭附加控制会话应断开控制关系，不关闭不属于该会话的服务浏览器。
- 明确的 CDP 服务停止才回收该服务拥有的浏览器与临时资源，保留显式 profile 数据。
- 控制面无法保证回滚已执行网页动作，不能在重连时自动重放未知结果的修改性步骤。

### 8.5 本地文件、下载与录制

CDP 在跨文件系统场景不是任意文件的自动传输协议。

- 原生工具经适配器使用 CDP 时，继续由主通道文件处理层完成输入暂存、路径映射和产物回传。
- 独立外部 CDP 客户端的浏览器侧文件路径按运行时路径解释；文档必须列出可访问目录和产物取回方法。
- 外部客户端将截图字节保存在宿主机，是客户端职责；浏览器产生的下载文件则必须有明确落盘及取回路径。
- 不承诺任意第三方客户端无需配置即可把宿主机绝对路径当成容器文件路径。

### 8.6 独立健康检查

分开报告：

- 容器进程存活；
- 执行代理协议就绪；
- 上游 CLI 版本可用；
- 主通道浏览器烟雾测试结果；
- CDP HTTP 发现就绪；
- CDP WebSocket 握手与无副作用协议调用成功；
- 浏览器退出、配置错误或文件不可写的具体原因。

移除“CDP 失败后用 doctor 成功掩盖”的逻辑。周期健康检查使用 `Browser.getVersion` 等无副作用请求，不持续开标签页、不刷新业务页。启动等待有截止时间和真实就绪证据，不使用固定睡两秒作为就绪保证。

## 9. 容器与浏览器安全加固

### 9.1 加固目标与限制

本次降低浏览器漏洞影响面、意外宿主机写入面和资源耗尽风险，不改变网络及业务策略。不能宣称 Docker 因此达到虚拟机级隔离，也不能宣称浏览器容器会约束宿主机 pi 的全部工具权限。

### 9.2 权限与系统调用

1. 在独立测试容器移除 `SYS_ADMIN` 和 `seccomp:unconfined`。
2. 优先使用 Docker 默认系统调用过滤。
3. 如果启用 Chromium 沙箱确实需要用户命名空间相关调用，采用版本化的最小定制过滤文件，并记录新增调用、理由和测试。
4. 评估 `cap_drop: [ALL]` 与 `no-new-privileges:true`；配套选择可在无额外提权下运行的 Chromium 用户命名空间沙箱。
5. 不同时依赖 setuid 沙箱提权和禁止提权配置却假装已验证兼容。
6. 保留非 root 浏览器用户、现有桥接网络和独立进程空间；不挂载 Docker socket、不使用特权容器或宿主机 PID 命名空间。

加固失败不能自动回退到宽权限并继续显示通过。保留旧部署供人工回滚，不作为新方案的隐式降级路径。

### 9.3 真正启用并验证 Chrome 沙箱

上游文档说明容器检测会自动添加 `--no-sandbox`。仅删除 Compose 的两个放宽项不足以证明 Chrome 沙箱开启。

必须核查固定 `0.36.0` 的实际启动实现：

- 优先寻找已存在、可验证的沙箱强制启用机制；
- 若不存在，维护最小上游补丁，增加桥接部署专用的“沙箱必须启用”运行配置；
- 自定义配置必须标为自研，不冒充上游已经支持的环境变量；
- 要求沙箱的模式不得自动添加或接受禁用沙箱的参数，冲突时明确报错；
- 沙箱不可用时新实例启动失败，不能静默回退；
- 主通道、脚本实例、profile 实例及 CDP 服务都必须采用一致的已加固启动路径。

验收结合浏览器实际启动参数、Chromium 沙箱状态和代表性渲染进程的隔离状态。仅“非 root”“没有看到某个参数”或“页面能打开”均不是充分证据。

### 9.4 文件系统与资源

- 配置文件、浏览器可执行文件及执行代理尽量只读。
- 目前 Chrome 安装文件与凭证状态同在 `data` 下，应在不迁移/丢失凭证的前提下，为浏览器安装子目录建立只读视图，或使用已验证的镜像内浏览器；具体变更要有回滚映射。
- 镜像根文件系统目标为只读；为临时目录、运行目录、浏览器缓存和其他确有需要的位置提供有界可写挂载或临时文件系统。
- `data`、profile 和密钥文件按容器运行 UID 与最小权限管理；禁止一把递归权限修改影响共享项目、备份或密钥。
- 宿主机产物目录仍允许按原功能写入，通过后端处理权限差异，不要求用户放宽到所有人可写。
- 保留 1 GiB 共享内存，依据实测设定 CPU、内存和进程数限额，记录最终数值与峰值证据。
- 容器只采用一套明确的 PID 1/子进程回收机制，避免无意义的多层 init。
- 补齐 `ffmpeg` 等承诺功能所需依赖，并锁定可维护版本。

### 12.3 回滚触发条件与动作

以下任一情况触发停止上线或回滚：数据解密失败、profile 损坏/冲突、核心模式失败、CDP 不可连接、取消失效、意外策略改变、沙箱静默关闭或容器权限重新放宽。

回滚流程：停止新任务 → 保存已完成显式产物 → 关闭新方案拥有的浏览器 → 恢复旧脚本/配置/唯一扩展源/镜像 → 保留新版本诊断 → 验证旧主通道与数据完整性。

如果新浏览器版本改变了 profile 格式，只能使用升级前一致性备份恢复，不能假设旧版 Chrome 必然能读取已升级的数据目录。应尽量避免在桥接开发中顺便升级真实业务 profile 的浏览器主版本。
